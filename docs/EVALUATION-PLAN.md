# 平台「固定地址」评估与执行方案 v1（供三方评审）

> 目标：找到最安全、最高效、最不容易搞错、框架清晰、以人为本的操作方式。
> 本文由 DSH 起草，交 Codex 评估，用户拍板。

---

## 0. 三条总原则

```text
1. 安全第一：发布一律先 dry-run，绝不真实发送；每次改动前先备份。
2. 一次只改一个变量：改完验证，再下一个。
3. 以人为本：人只做“关键决策”，其余自动；一个工作台看全流程，不混淆。
```

---

## 1. 现状盘点（已存在，别推翻）

```text
平台层：
  统一工作台（队列 + 状态标签）
  两引擎：本地模板(旧) + VibeMotion(新)
  三风格：简洁 / 严谨工业 / 活泼动感
  45 项图形库 + 数字人口播(可选) + 火山TTS + 内容感知选图
  素材库（图片/声音 已分组/标签/归档）、账号组、公众号草稿、视频号发布包

已发现的主要问题（见两份全局清单）：
  发布边界不严谨、任务版本/取消不一致、自动样片质量未达标、两引擎数据分裂
```

---

## 2. 战略方向（三方已基本对齐）

```text
最终只保留 VibeMotion 一个渲染引擎。
旧引擎能力 → 变成 VibeMotion 里的「固定页式」模式。

关键区分：
  模式 = 怎么编排页面、编辑字段、预览（讲解式 / 固定页式）
  风格 = 配色、字体、视觉（简洁 / 工业 / 动感）
```

---

## 3. 分阶段执行方案

### 阶段 0 · 安全基线（半天，DSH）

```text
- git tag + DB 快照（VACUUM INTO）
- 记录素材清单、版本号
- 定测试账号策略（默认 dry-run，绝不真实发送）
验收：可回退基线 + 测试策略明确
```

### 阶段 1 · 修地基（1–3 天，DSH）

```text
A. 发布边界：
   - 草稿 ≠ 已发布，拆成两步
   - 账号必选，不静默回退默认账号
   - 回执：账号/渠道/产物版本/media_id/链接/幂等键
   - 默认 dry-run
B. 任务一致性：
   - 改文案 → 旧配音/旧审批/旧发布全部失效
   - 取消真终止渲染；重试/重启有状态机；完成回写校验 attempt
验收：
   - 两账号 dry-run 无真实写入
   - 草稿不会被记成 published
   - 改稿不复用旧语音；取消不回 done；重启状态可恢复
```

### 阶段 2 · 并行做新能力（3–7 天，Codex 渲染 + DSH 对接）

```text
A. 固定页式 4 页原型：
   把旧引擎的页式迁进 VibeMotion（只做新建组件 + 一条样片，不碰数据）
   验证：逐页预览、文案、封面、音乐混流
B. 自动样片闭环：
   修空稿写作、真实配音时长、分句字幕、8–12 场景、双尺寸封面
   先打通 5–7 种常用图解自动选型
验收：
   平台新建（非 CLI 专用数据）出一条接近样片A，可改可重渲，有抽帧
```

### 阶段 3 · 统一接入（2–4 天，双方）

```text
- 把固定页式 + 自动样片接进统一工作台
- 两引擎读模型统一：成片库 / 审批 / 发布 覆盖两引擎
- 一个内容 = 一个工作项 + 全部版本/渠道可追溯
验收：两引擎都能从工作台走到手动包/草稿
```

### 阶段 4 · 收敛与收尾（3–5 天，双方）

```text
- 新建默认走 VibeMotion；旧引擎降级为「固定页式模式」
- 历史项目保留原成片；需要重渲的有迁移路径
- 公众号配图依赖迁成 Remotion Still
- 备份恢复演练、许可台账、合规复核、容量归档
验收：隔离恢复成功；清理先 dry-run；旧执行器可下线
```

---

## 4. 风险与安全护栏

```text
1. 真实发送风险 → 默认 dry-run，发送前展示账号/版本/素材摘要，二次确认
2. 错版风险 → 每次渲染用独立输入快照，不覆盖共享分镜/样式
3. 串稿风险 → 渲染加全局锁 + attempt-id
4. 数据丢失 → 每个阶段前 commit + DB 快照
5. 混淆风险 → 工作台统一“模式/风格”命名，不做两套入口
```

---

## 5. 需要 Codex 重点评估的 6 个问题

```text
1. 阶段顺序是否最优？有没有更安全的替代顺序？
2. “固定页式模式”和“讲解式模式”的边界怎么切最清晰？
3. 旧 spec 字段级映射，哪些能自动转、哪些必须人工？
4. 10–18 人日的估算是否合理？能否拆成更小的可验收里程碑？
5. 发布边界和任务一致性，DSH 的修法是否有遗漏？
6. 从“以人为本”角度，工作台还应补哪些“人只做关键决策”的入口？
```

---

## 6. 需要用户拍板的决策点

```text
1. 是否同意“最终只留 VibeMotion，旧引擎=固定页式模式”？
2. 发布默认 dry-run，真实发送必须手动开启并二次确认？
3. 先做阶段1（地基），再并行阶段2，还是想先看固定页式样片？
4. 历史旧项目：优先“原样保留”，还是优先“可重渲”？
```

# 一句话

```text
先补地基（发布边界+任务一致性），
再并行做固定页式原型和自动样片闭环，
最后统一接入、收敛引擎、收尾。
全程 dry-run + 备份 + 一次一个变量。
```
