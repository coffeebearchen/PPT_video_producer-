# 全局代码问题清单（DSH 视角）

> 从全局角度审视当前代码，列出问题与风险，供明天统一决策。

## A. 架构 / 一致性

```text
1. 两套引擎并存，数据模型不统一：
   - 引擎1：briefs + specs + renders + publications
   - 引擎2：video_tasks（单表）
   统一队列靠运行时拼接，长期维护成本高。

2. 发布流程未完全统一：
   - 引擎1 有完整审批/发布包/公众号
   - 引擎2 刚接“准备发布/生成发布包/公众号草稿”，
     但“群发/定时/回执”未对齐。

3. 老页面仍存在：
   选题/审批/发布 三个页面还没降级成工作台标签，
   菜单虽然收敛了，但底层路由和逻辑还在两套。
```

## B. 视频引擎（VibeMotion）

```text
4. 自动生成的质量还没完全追上 Codex 样片A：
   buildTimeline 的 GraphicScene 分支是简化版，
   与 Codex 的 ChalkBoard + 逐帧绘制还有差距。

5. 三风格已接，但 45 项图形库还没全部接入“自动编排”，
   当前按结构类型映射了少量 family/kind。

6. 内容感知选图是“关键词包含”匹配，简单但不够智能；
   Lottie 仍是随机。

7. 数字人口播是模拟口型，非精确口型；
   真实头像上传需校准，未接数字人服务。
```

## C. 数据 / 文件 / 回滚

```text
8. 引擎输出目录分开，但缺少自动清理：
   data/media/<renderId>/ 和 data/media/video-tasks/<id>/
   会越积越多，没有归档/清理策略。

9. 运行时会产生未跟踪文件：
   style.settings.json、timeline_dsl.json、out/、音频 mp3
   已加入 .gitignore，但新环境需要 npm ci 才能跑。

10. GitHub 推送不稳定（网络重置），多次失败，
    需要网络稳定时手动 push origin main。
```

## D. 配置 / 凭据

```text
11. 凭据存 SQLite settings（不依赖 .env）：
    wechat / llm / tts 的 key 都存 DB。
    好处是界面可配；风险是 DB 泄露 = key 泄露。

12. 火山 TTS 已接，但未用真实 Key 验证；
    OpenAI 兼容 / MiniMax / 讯飞 / 硅基流动 只留配置未实现协议。

13. 公众号 dry_run 开关是账号级，
    测试时曾触发真实 draft 创建，需注意。
```

## E. 合规 / 安全

```text
14. 合规闸门是简单关键词（保证/百分百/最/第一…），
    会误伤“最”等常用字，也漏掉复杂违规表达。

15. 视频号无官方发布 API，保持手动上传（正确）；
    但“发布包”要确保不误触发自动发布。

16. 引用素材许可表还没建全（Open Doodles/Lottie/字体来源）。
```

## F. 体验 / 一致性

```text
17. 侧边栏已收敛，但“素材库”一词有歧义：
    “素材库”= 成片版本库，“图片素材”= 图片资产。
    对用户容易混淆。

18. 工作台“待发布”只标记状态，未直接跳转到发布页，
    还差“一键到发布”的衔接。

19. 老引擎1 的“创作台/选题”概念与新引擎2 的“新建视频”并存，
    名词不统一。
```

## G. 明天建议的优先级

```text
P0：统一发布流程 + 老页面降级（让人不再混淆）
P1：把 Codex 样片A质量 + 45图形库接回自动编排
P2：素材/输出目录的归档与清理
P3：合规闸门升级 + 素材许可表
```
